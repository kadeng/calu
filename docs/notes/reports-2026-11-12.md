## Terminal client, step one: what the documentation should say

**Install and start**
- `uv sync --all-extras`, or `pip install 'calu[tui]'`.
- `calu attach [ADDRESS --token T] [--session ID]` starts the full-screen client when stdin and stdout are a terminal.
- `calu attach --plain` is the line client. A pipe, `TERM=dumb`, `CALU_ATTACH=plain` or a missing Textual also give the line client; the last prints one line on stderr saying so.
- `CALU_TUI_THEME=calu-light` picks the theme at start; `/theme` changes it.
- `uv run python -m calu.tui [showcase|escalation|question_multi|two_subagents|simple_turn|stopped|long_session]` runs the client on a scripted session without calu running.
- `ctrl+d` detaches and the session keeps running. Afterwards the terminal shows the session id and state, how many steps wait, and how to attach again. Exit code is 0 after a detach and 1 if the session closed the connection.

**README, "Four front ends"**
The terminal client is now a full-screen client. Suggested text: "a full-screen terminal client (`calu attach`): one line per step with the checker's verdict, a decision card that never blocks typing or scrolling, a tab per subagent, side questions (`/btw`), usage and quota; `calu attach --plain` is the line client for pipes and scripts".

**CALU_GUIDE, attach section: what to explain**
- The screen: status bar; agent tabs; transcript; decision card; composer; side panel with NEEDS YOU, AGENTS, QUEUE, HONESTY and SESSION (a column from 110 columns, `f2` below that).
- The typing rule: the decision keys act only while the input is empty; `a` and `d` need a second press, and any other key after the first is typed.
- `/btw`: answered by Claude Code from the conversation as it stands, without tools; the turn goes on, and the question and answer never enter the conversation or the checkers' context.
- `/model` changes the model of a running session from Claude's next step. The effort is fixed at start: `/effort`, then `/stop` and `/start`.
- Quota appears when Claude Code announces a limit; an API-key or Bedrock account has none.
- Mouse selection needs shift (option in iTerm); `alt+c` copies through OSC 52 (tmux: `set -g set-clipboard on`).
- A screenshot: `scripts/tui_screenshots.py DIR` writes them; `03-subagents-question-120x36` is the most complete.

## Terminal client, step one: protocol gaps

- Subagents: only a running background subagent takes messages, and only relayed by the main agent (one main-agent step per message). Foreground and finished subagents take none. The composer says so and sends to main.
- Subagents: no stop of one subagent (palette entry 'not available from this session: interrupt ends the whole turn'). The CLI has a `stop_task` control request and the SDK a `stop_task` method that a later `agent.stop` could use.
- Subagents: no text deltas, no per-agent state, tokens, model or times in `AgentInfo`. The client derives the state from events and shows 'running, no activity seen since attach' after a late attach.
- Queue: `chat.queue` is read-only. No request withdraws, edits or reorders a queued message (the palette entry says so). The CLI has a `cancel_async_message` control request that a later `chat.cancel` could use.
- Effort: cannot change in a running session (`/effort` applies at the next `/start`). There is no model list from the session (static aliases plus free text; the CLI has a `list_models` control request). No event announces a `model.set` by another client: the session writes a log line and the client learns the new value from its next snapshot.
- Usage: limits arrive only when Claude Code announces a change of state, so an account inside its limits shows 'no limit reported'. There are no token counts per turn or per step and no checker spend total. The context fill is asked by the client after attach and after each turn, not pushed.
- Permission mode of Claude Code is not in the snapshot, only in a log line. It is not shown and is listed as not available.
- Escalations: no opened-at time on `escalation.request` or in the snapshot, and no `resolved_by` in `escalation.resolved` (the client says 'decided elsewhere'). No list of past escalations, no decision with edited input, no rule creation from a decision.
- Questions: one free-text `answer` for a whole set (the client composes it), and `escalation.resolved` reports an answered question as `deny` (the client remembers the kind and shows ANSWERED).
- Timing: live events carry no timestamp, and the protocol client drops `RecordedEvent.time` on replay. Durations and waiting times exist only for what happened while attached.
- Checks: `check.result` has no checker name, model, tokens or duration, and there is no context request for a step that was not escalated. `tool.result.content` may be shortened with no way to fetch the rest.
- `user.input` names neither the queue entry it consumed nor its target. The client matches a relayed message by the text of the queue entry.
- Background tasks: only a count at turn end.
- Side questions: the answer comes back whole, with no streaming. The Agent SDK has no public method, so `SdkRunner.side_question` sends the control request through the SDK's private `_query._send_control_request`; re-run `spikes/side_question.py` after an SDK or CLI update.
- File comments need the project directory on the client's machine; the protocol has no file read. The client says so when the directory is missing.

## Terminal client: a reviewer's summary

Not ready to ship: two blocking defects, both reproduced. A decision can land on a step the user never looked at, and f4 ends the client for good after about 40 seconds in the git program.

**What I ran, at ca5d4ab in the worktree (changed no file; worktree clean afterwards)**
- `uv run pytest -q -m 'not live and not db'`: 1367 passed, 2 failed. Both failures are `tests/unit/test_handoff_counts.py`, as the engineers reported (20 requests against 17 in HANDOFF.md, about 55.6k source lines against 39.5k).

- Probes under Pilot against `FakeSession` for the decision paths, a websockets keepalive probe, and a pty run of `python -m calu.tui` with `CALU_GIT_TOOL='sleep 30'`.

**Blocking**
- **Wrong step decided.** The first `a` or `d` and the note question of alt+a are bound to "whatever the card shows when the next key arrives". If the first escalation is resolved elsewhere in between, the second `a`, or Enter on the note question, allows the next one.
- **f4 detaches.** The git program runs as a blocking `subprocess.call` on the event loop. The server's keepalive closes the connection with 1011 after about 40 seconds, and `Link` reconnects only after 4002. The report's "attaches again by itself" is not true for this case.

**Should fix**
- ctrl+c inside the git program ends the client (reproduced).
- A 4002 close that arrives during `state.get` is treated as final (by reading, not reproduced).
- Checker saves and `/honesty MODE` report success without checking that the attached session reads the same database.

## Honesty, step state (as built): design choices made

- Content hashing is done by calu in Python: SHA-256 for the verified map and `trusted_files`, plus the git blob id for comparison with the baseline tree. git is only asked for names and ids (`rev-list`, `rev-parse`, `ls-tree`, `ls-files`), so no content filter or diff program configured in the repository runs. Consequence: a repository that relies on autocrlf or clean filters sees such files as unreviewed (fail closed) until an edit or a review verifies them.
- A file's hashes are cached by size, mtime, ctime and inode, and only for files whose last change is at least 2 s old. On the calu repository, `unreviewed()` took about 20 ms the first time and 8 ms afterwards.
- Baseline order is that of `git rev-list` from HEAD, limited to 5000 commits; the first commit trusted by commit id or tree id wins. All ids are looked up with one query.
- Every git failure fails closed: no baseline, `Unreviewed(everything=True, problem=...)`, or `uncertified()` returning a reason. `find_baseline` propagates a database error; the caller must then treat the session as having no baseline.
- Deleted files are not unreviewed and do not block certification. Submodule entries the baseline records are not looked into. Any other directory git lists as one entry (a nested repository) is always unreviewed.
- The state works on the whole repository even when the workspace is a subdirectory. Paths are workspace-relative; a file outside the workspace is named by its absolute path.
- Ignored files and files outside the repository are tracked only after `watch(path)`. `record_edit` and `apply_review` watch their file automatically.
- `trusted_files` is read whole into `HonestyState.trusted_hashes`; a trusted hash verifies any file with that content, tracked files included.
- Clean marks are applied before dirty ones, so a spot named in both lists of one answer stays open. A dirty mark on an already open spot refreshes its reason.
- In a parsing Python file a clean mark's symbol is first read as the definition it names: the bare `run` means the function `run`, not `Parser.run`, when both exist.
- `apply_review` clears 'review required' only when no mark is open afterwards, and sets it when the findings exceed the threshold. A result without a valid SHA-256 changes nothing for its file. A person's `clear` never changes 'review required'.
- `close_stale()` and `snapshot()` are separate calls; `snapshot()` does not change the state. The session must call `close_stale()` first.
- Re-certifying a trusted commit or hash keeps the first row and returns False; the CLI prints 'was trusted already'.
- `calu honesty trust` records the OS user name (`getpass.getuser()`) as `certified_by`. `--file` stores the absolute path as the hint and hashes a symbolic link as its target text, as git does.
- `calu honesty trusted` shows the newest 50 commits unless `--all` is given, then all trusted file contents.
- `calu honesty untrust COMMIT` first resolves the name with git in the current directory; if git cannot, it takes a unique hexadecimal prefix of a trusted commit id.
- The note for checkers is always non-empty, also for a clean state. Mark reasons appear in it unfenced, as in the present `register_note`.
- Reviewer budget settings and defaults: `review_batch_files` 8, `review_concurrency` 4, `reviewer_request_limit` 30, `reviewer_output_tokens_limit` 60000, `review_timeout_s` 600 (for the whole review). `max_open_marks` accepts 0, meaning any mark requires a review.

## Honesty, step state (after corrections): design choices made

- Migration 0027 was edited in place rather than adding 0028, because it is unpublished and exists only on this branch. A database that already ran the old 0027 (only the private test server, whose tests create fresh databases) would need to be recreated.
- On a strengthening certification the row's tree_id (commits) or path (files), certified_by, certified_at, note, session_id and recorded_as are all replaced by the new certification's values.
- A tree's source is the strongest source among the commits recording that tree; a baseline found by commit id and tree id gets the stronger of the two.
- `Baseline` is a subclass of `GitCommit` with a `source` field, so `state.baseline.commit_id` and `.short` keep working. A `Baseline` does not compare equal to a plain `GitCommit`.
- The state itself ignores a baseline whose source is weaker than `sufficient_trust` (`_base()`), in addition to `find_baseline(minimum=...)`, so a missed recomputation after a settings change cannot leave a weaker baseline in force.
- A partial edit always records `check`, whatever the source of the content it started from. A file verified by review at content H and then edited is `check` at the new content.
- `apply_review` keeps verifying a file in memory at the reviewed content even with findings (the reviewer accepted this for `record_edit`), so the edit that fixes a finding starts from a reviewed basis. `storable()` keeps such content out of the database.

- `expect_edit` and `record_edit` verify nothing for a path that is a symbolic link; the link's target is watched instead.
- `trusted_file_sources(hashes=None)` reads the whole table by default, with an optional list of hashes for a targeted lookup once the table is large. The `calu.store.trust` module docstring states the size: at most one row per checked edit and per reviewed file, about 300 bytes each.
- `calu_prune_trust` writes one audit row per table with the count, not one per deleted row. `--days 0` is allowed and removes every `check` and `review` row.
- Pruning also removes `check` and `review` rows of trusted_commits, not only of trusted_files; a session whose baseline is pruned gets `trust_changed` and may then have no baseline.
- The marker variable is named `CALU_INSIDE_SESSION` and lives in `calu.paths`, which imports nothing from calu.
- The note's baseline line now reads `Baseline: trusted commit <id> (trust established by: <source>).`
- The lock is one reentrant lock held for a whole public call, so a slow `unreviewed()` makes other callers wait. Attributes set directly by the session (`baseline`, `trusted_hashes`, `sufficient_trust`) are plain assignments.


## Honesty, step state (after corrections): what the documentation should say

**Sources of trust.** Every trusted commit and every stored file content records who established it: `user` (a person), `review` (calu's honesty review) or `check` (calu's step checkers judged the edit without leaving a mark). The order is user > review > check. A stronger certification replaces a weaker record of the same commit or content, never the reverse.

**Setting `honesty.sufficient_trust`** (`check` | `review` | `user`, default `check`): the weakest source that counts.
- A commit with a weaker source is no baseline; a file content with a weaker source is unreviewed.
- With `review`, a checked edit alone leaves the file unreviewed until an honesty review judged it. With `user`, only a person's certification counts.
- Raising the setting deletes nothing; lowering it makes weaker records count again.

**Command line.**
- `calu honesty trust <commit-or-branch> [--note TEXT]` and `calu honesty trust --file PATH` record `user` with the OS user name and replace a weaker record. If a `user` record exists they print "was trusted by a user already".
- `calu honesty trusted [--all]` lists commits and file contents, each with its source. Without `--all` it shows the newest 50 of each.
- `calu honesty prune --days N` removes `check` and `review` records older than N days from both tables and never removes `user` records. A session whose baseline was pruned looks it up again and may then have none.
- All of these use the `operator` credential (or `admin`), so a `user` certification from the command line rests on the protection of the credential store.
- `calu honesty trust`, `untrust` and `prune` refuse to run inside a calu session: calu sets `CALU_INSIDE_SESSION=1` for Claude Code and everything it starts. A person runs them in a terminal of their own, or uses `/trust` in a client once that exists. `calu honesty trusted` still works there.

**Behaviour to describe.**
- A checked edit verifies a file only if the file afterwards has exactly the content the checkers judged. If anything else changes the file between the check and the tool's result, the file is unreviewed.
- Edits through a symbolic link, of non-UTF-8 files, of files over 8 MB, or where the tool converts line endings are not verified by the edit check; an honesty review verifies them.
- A submodule counts as reviewed only at the commit the baseline records for it. calu does not look inside submodules, and a commit that adds or moves a submodule entry is certified only by a person.
- In repositories that convert line endings or apply content filters on checkout, converted files are unreviewed until verified, and commits of them are certified only by a person.
- The baseline search is bounded to 5000 commits, as before.
- `trusted_files` grows by at most one row per checked edit and per reviewed file; `calu honesty prune` is the way to bound it.
- Notification channel `trust_changed` is sent for commit certifications, for `user` file trust, and for removals and prunes. It is not sent for a session's own `check` and `review` file records.

## Honesty, step review (as built): deviations from the specification

- Whitespace-only is defined narrowly: two contents are equal after removing trailing whitespace and line endings of every line and dropping blank lines. A change of indentation or of whitespace inside a line is not whitespace-only and goes to the reviewer, because indentation can decide what code does.
- Section 4 says a failed review escalates. A review that ran but could not judge some files (too large, not text, staged-only) also escalates the step, naming them, although the review itself did not fail; `honesty.review` then answers `ran: true` with a `problem`.
- 'Do not repeat a review when nothing changed' also applies to a failed review: the gate does not retry it by itself. The step is escalated with the old failure and the note that `/honesty-review` runs it again. A transient model error therefore needs a person or a change of the files.
- 'Not more than one review at a time': a second caller joins the running review and gets its answer; it does not queue a review of its own afterwards.
- The gate does not wait for a whole review. It waits within its own limit of 420 s per step, less the time the checkers took and a 20 s margin. A longer review (default limit 600 s) goes on as a task of the session, the step is escalated with 'still running', and the result is applied when the review ends.
- With `honesty.sufficient_trust = user` the gate starts no review, because a review cannot verify a file then; the step is escalated with that reason. A person's `/honesty-review` still runs, for its findings and to clear 'review required'.
- Without a baseline the gate escalates without a review, as section 5 says. A review a person asks for then judges every file git lists, whole, and calu certifies HEAD with the source 'review' if every content HEAD records is verified. The specification names the review as a way out of 'no baseline' but does not say how; this is my reading. It is limited by the cap of 300 files.
- The cap counts every file that is unreviewed or marked, before the whitespace shortcut, so that no file is read when the cap is exceeded.
- A marked file is always given to the reviewer whole with its recorded marks, not as a diff, and never takes the whitespace shortcut. The diff for other files is computed by calu from the bytes it hashed, not taken from `git diff`.
- A review result is dropped for a file whose content or open marks changed while the review ran; the specification does not mention this case. The file stays as it was and is named in the review's problem.
- Progress uses no new event: `honesty.update` (`review_running`) and `log` lines. The specification allowed either.
- Carried over from step two, not changed: the dirty marks of command-route checkers and of a commit's changeset checkers are recorded when they answer, also for a denied step, because they name code that already exists. Section 2 says marks are applied only after the tool call succeeded. Marks of edits follow the specification.


## Honesty, step review (as built): design choices made

- Reviewer budget defaults are unchanged from step one: 8 files per batch, 4 batches at once, 30 requests and 60,000 output tokens per batch, 600 s per review. New fixed limits: 120,000 characters of file text per batch (`BATCH_CHARS`), 200,000 bytes per file (`REVIEW_FILE_BYTES`).
- The reviewer answers by file number, not by path, so a path with unusual characters cannot break the mapping. `honest` must agree with `findings`, otherwise the batch fails.
- The reviewer's instructions tell it to answer `honest: false` with a finding when it cannot decide about a file. There is no third verdict.
- The reviewer's prompt is not a checker type: it is the fixed `system/honesty-review.md` plus `honesty.rules`, and cannot be edited with `calu checker edit`.
- A review counts only as a whole: one failed batch discards the results of the others, and the whitespace shortcuts of that review are not applied either.
- The review is cancelled when the run of the session ends; nothing of it is applied.
- The whitespace shortcut records the source 'review'.
- 'Review required' is cleared only when no mark at all is open after the review (the existing `apply_review` rule). With findings left it stays set, and the next gate attempt is denied with the marks until one of the files changes.
- The certifier name of everything a review stores is 'calu honesty review'.
- `calu attach` runs `/honesty-review` in a background task so that escalations can be answered while it runs.
- The honesty reviewer is listed in the start-up model warnings only while `honesty.mode` is not off.


## Honesty, step review (as built): what the documentation should say

The honesty review
- What it does: a reviewer agent judges the files that are unreviewed or carry marks against the honesty rules. An honest file is verified at the content the reviewer was shown and stored with the source `review`. Findings become that file's marks. "Review required" is cleared when no mark is left.
- When it runs: by itself in `honesty.mode = enforce`, when a command that executes project code or a `git commit` meets unreviewed files or "review required" (not with open marks alone, not without a baseline). On request in `track` and `enforce`: `/honesty-review` in `calu attach`, "Review now" in the web live view, protocol request `honesty.review`.
- One review at a time. calu does not start it again while nothing changed since the last one, also after a failure; `/honesty-review` always runs one.
- Outcome at the gate: clean, the step runs; findings, the step is denied with them; failed, over the cap, still running or files it cannot judge, the step waits for a person. A person's allow runs the step once and certifies nothing.
- A change that is only trailing whitespace, line endings or blank lines is verified without a model. Indentation changes are reviewed.
- Not read by the review: files over 200,000 bytes, files that are not UTF-8 text, symbolic links and submodules, and a staged content that differs from the working file. A person certifies those with `/trust-file PATH` or `calu honesty trust --file PATH`, or stages the file again.
- More than `honesty.review_max_files` (300) files: no review; the escalation names the count.
- A step waits for a review at most about seven minutes less the time its checkers took. A longer review continues, the step is escalated meanwhile, and the result is there at the next attempt.
- Repository without a trusted commit: `/honesty-review` judges every file git lists (up to the cap). If every file HEAD records is then verified and the working tree has no other contents, HEAD is certified with the source `review` and becomes the baseline. Otherwise the log says why not.
- `honesty.sufficient_trust = user`: calu starts no review by itself; only a person's certification verifies.

Settings (all in docs/CONFIGURATION.md)
- `honesty.reviewer_model`: blank uses the default model. It needs that provider's key; start-up warnings and `calu doctor` list the "honesty reviewer" while the mode is not off.
- `honesty.review_max_files` 300, `review_batch_files` 8, `review_concurrency` 4, `reviewer_request_limit` 30, `reviewer_output_tokens_limit` 60000, `review_timeout_s` 600.

What a user sees
- Terminal and attach: `honesty: review started: N file(s) to judge (...)`, `honesty: review: batch i of n answered`, `honesty: review finished: X file(s) verified, Y finding(s), Z file(s) not judged (... tokens)`, and the state line with "a review is running".
- `/honesty-review` prints `[honesty] review requested` at once and `[honesty] the review ran` or `[honesty] no review ran: <reason>` at the end; other commands can be typed meanwhile.
- `calu honesty trusted` shows what a review stored with the source `review` and the certifier "calu honesty review".

For PLAN.md: the reviewer's instructions are fixed plus the honesty rules; the review's cost is not in `checker_runs`; the call-graph wave review remains the owner's later answer to the cap.

## Honesty, step review (after corrections): design choices made

- The record of the last review holds, for a judged file, the content reviewed and its marks after the result was applied. A review that ends with findings is therefore not repeated on every gate attempt while review is required.

## Honesty, step review (after corrections): what the documentation should say

- **Review without a baseline:** only a person's `/honesty-review` (or `honesty.review`) reviews a repository without a baseline and can certify HEAD afterwards. A review calu starts by itself never runs without a baseline and never certifies a commit.
- **Files that change during a review:** their result is dropped and the same request reviews them again, up to three reviews in a row. If a file still changes, the step is escalated with "N file(s) changed while the honesty review ran: ... The next review reads them"; the next step that needs a clean state starts a review of them.
- **No repetition:** calu does not start a review by itself while the last review looked at every file a new one would read, with the same content, marks and baseline. `/honesty-review` always runs one.
- **Failed review:** the step that needed it is escalated. calu starts the next review by itself 60 s after the failure at the earliest; `/honesty-review` runs one at once, for example after correcting `honesty.reviewer_model` or a key.
- **Size limits:** the reviewer gets a file's change against the baseline, or the whole file where the baseline does not hold it. Not judged, and left to `/trust-file PATH` or `calu honesty trust --file PATH`: a file whose text for the reviewer is over 200,000 bytes, a file over 2,000,000 bytes, and a file that is not UTF-8 text.
